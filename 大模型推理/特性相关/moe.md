## 1. 从 Dense FFN 到 MoE：为什么需要专家？

本章回答：MoE 想解决什么问题，又引入了什么代价？

### 1.1 回顾 Transformer 中的 FFN

在常见的 Dense Transformer 中，每个 token 的隐藏状态都会经过所在层的同一组 FFN 参数。FFN 通常由线性变换和非线性激活组成，不同模型也可能采用门控结构。

**写作要点：** 交代 Attention 与 FFN 在 Transformer block 中的位置；说明 FFN 对每个 token 的隐藏状态进行变换。后文图中若省略残差连接与归一化，需要注明。

> 配图占位：Dense Transformer block，突出 FFN 子层。

### 1.2 用稀疏激活扩展模型容量

稀疏 MoE 将部分 Transformer 层中的稠密 FFN 替换为多个专家 FFN，并通过路由器为每个 token 选择少量专家参与计算。这样，模型可以增加总参数量，而不让每个 token 的专家计算量随专家总数同比增长。

这里的选择发生在 token 经过每个 MoE 层时；常见稀疏 MoE 的训练阶段也使用路由。专家通常由训练形成分工，不宜直接等同于人为预设的“数学专家”或“编程专家”。

### 1.3 总参数量、激活参数量与部署成本

| 概念 | 需要解释的问题 |
| --- | --- |
| 总参数量 | 全部专家与非专家模块一共有多少参数？ |
| 每 token 激活参数量 | 某个 token 实际使用了哪些模块的参数？ |
| 实际部署成本 | 权重、KV Cache、中间张量、通信缓冲分别占用什么资源？ |

少量专家参与某个 token 的计算，并不意味着只需存储这些专家的权重；同一批次中的不同 token 也可能覆盖许多专家。

**衔接下一章：** 确定稀疏激活的目标后，展开 MoE 层内部结构。

## 2. MoE 层的基本结构：有哪些组成部分？

本章回答：输入隐藏状态如何变成多个专家输出的组合？

### 2.1 Router：为专家打分

**写作要点：** 区分输入隐藏状态、路由分数、专家编号和路由权重；说明分数来自可学习的路由器，并非直接计算 token 与某个知识标签的相似度。

### 2.2 Top-K：选择参与计算的专家

**写作要点：** 定义专家总数 E 和每 token 选择的专家数 K；解释 Top-1、Top-2 等配置。以常见的 token-choice 路由为主线，其他方式在第四章补充。

### 2.3 专家 FFN 与加权合并

对一个输入隐藏状态 x，可用下面的简化表达式描述稀疏 MoE 子层：

$$
y(x) = \sum_{i \in S(x)} w_i(x)\,E_i(x)
$$

其中，S(x) 是选中的专家集合，E_i 是第 i 个专家，w_i 是用于合并输出的权重。权重的计算和归一化方式取决于具体模型；此处不包含残差连接，也暂不包含共享专家。

> 配图占位：输入 → Router / Top-K → 选中的专家 FFN → 加权求和。用灰色标出未被当前 token 选中的专家。

### 2.4 统一术语与张量符号

| 符号 / 术语 | 含义 |
| --- | --- |
| T | 本次所讨论计算范围内的 token 数，跨卡时注明是本地还是全组 |
| H | token 隐藏状态维度 |
| E | 所讨论 MoE 层的路由专家总数 |
| K | 每个 token 选择的路由专家数 |
| Dispatch | 将 token 分配到对应专家的执行过程，可能包含重排与通信 |
| Combine | 将专家输出按路由关系还原、聚合为 token 输出的执行过程 |

## 3. 单卡执行过程：一个 token 如何经过 MoE？

本章回答：从模型结构到实际矩阵计算，中间发生了什么？先假设所有专家都在同一张卡上。

### 3.1 贯穿全文的例子

统一使用 4 个 token、4 个专家、Top-2 的例子。假设路由结果及用于合并的权重如下；数值仅用于演示。

| Token | 专家一 | 权重 | 专家二 | 权重 |
| --- | --- | --- | --- | --- |
| t0 | E0 | 0.6 | E2 | 0.4 |
| t1 | E1 | 0.7 | E2 | 0.3 |
| t2 | E0 | 0.4 | E3 | 0.6 |
| t3 | E0 | 0.8 | E2 | 0.2 |

### 3.2 路由：得到专家编号与权重

**写作要点：** 用输入隐藏状态 `[T, H]`、专家编号 `[T, K]`、路由权重 `[T, K]` 串起数据关系。这些是概念形状，具体实现可能使用压缩表示或融合算子。

### 3.3 重排：按专家组织 token

| 专家 | 接收的 token | 分配数量 |
| --- | --- | --- |
| E0 | t0、t2、t3 | 3 |
| E1 | t1 | 1 |
| E2 | t0、t1、t3 | 3 |
| E3 | t2 | 1 |

**写作要点：** 4 个 token 形成 8 个 token–expert 分配；为什么按专家分组有利于批量计算；原始 token 索引、专家编号和权重如何保持对应。逻辑上的重复分配不等于实现必须显式复制所有数据。

### 3.4 计算：各专家执行 FFN

**写作要点：** 不同专家的输入行数可能不同；逐专家计算与 Grouped GEMM 的基本差异；此处解释执行目的，性能分析留到第七章。

### 3.5 合并：恢复顺序并生成输出

例如，t0 的输出为 `0.6 × E0(t0) + 0.4 × E2(t0)`。最终恢复为与原始 token 对应的输出序列，隐藏状态形状为 `[T, H]`。

> 配图占位：token 原始顺序 → 按专家分组 → 专家输出 → 按 token 恢复并加权合并。贯穿使用一致的 token 颜色。

**衔接下一章：** 例子中已出现 3、1、3、1 的负载分布，接下来讨论这种不均衡为什么重要。

## 4. 路由与负载均衡：专家为什么忙闲不均？

本章回答：路由策略如何同时影响模型训练和推理执行？

### 4.1 路由选择与专家分工

**写作要点：** 以 token-choice Top-K 为主线，可简要对比 expert-choice；解释专家分工由训练形成，避免将专家解释成固定知识库。

### 4.2 负载倾斜的来源与影响

**写作要点：** 统计每个专家接收的分配数量；区分单个专家负载和一张卡上所有专家的总负载；说明热点专家可能导致执行等待。

### 4.3 训练中的均衡机制

**写作要点：** 辅助负载均衡损失、路由偏置等思路；具体公式随选定模型补充。训练约束与推理时的专家放置、冗余副本分别讨论。

### 4.4 专家容量、Token Dropping 与 Dropless

**写作要点：** 容量约束解决什么问题；超过容量时如何处理；说明机制的适用阶段和实现范围，避免表述成所有 MoE 都必须采用。

### 4.5 结构扩展：共享专家与细粒度专家

**写作要点：** 区分始终参与计算的共享专家和按 token 选择的路由专家；解释专家粒度改变了什么。将这些内容标为架构变体，与基础例子分开。

## 5. 专家并行 EP：如何从单卡扩展到多卡？

本章回答：专家部署到不同设备后，执行过程增加了哪些步骤？

### 5.1 EP Group、Rank 与本地专家

**ep_size=N 表示每 N 张卡组成一个 EP 组，专家在这 N 张卡之间分配。**
每个组需要能够完成它收到的 token 的专家计算。一个 token 在某层可能选中该层专家集合中的任意专家，组内必须能找到相应权重。



专家并行（Expert Parallelism，EP）将专家分布在多个设备上。一个 EP group 中的 rank 协同完成该执行范围内的专家计算。全局专家编号到本地专家的映射由具体部署和实现决定。

**写作要点：** 区分专家数、设备数和组大小；说明一个 rank 可以持有多个专家；基础例子先不引入专家 TP 或冗余副本。

### 5.2 将贯穿示例扩展为两张卡

| EP Rank | 持有的专家 | 初始持有的 token |
| --- | --- | --- |
| Rank 0 | E0、E1 | t0、t1 |
| Rank 1 | E2、E3 | t2、t3 |

沿用第三章的路由结果，标出本地和跨卡的分配。例如，t0 需要分别在 Rank 0 的 E0 和 Rank 1 的 E2 上计算。

### 5.3 跨卡 Dispatch 与 Combine

**写作要点：** 用“源 rank → 专家所在 rank → 源 rank”解释逻辑上的往返过程；通信结果需要恢复到 token 与权重的对应关系。具体聚合位置和通信调用在下一章展开。

> 配图占位：两张卡的专家布局、token 来源、dispatch 箭头与 combine 箭头。

### 5.4 EP 与 TP、DP、PP 的关系

**写作要点：** 分别解释“分专家、切张量、复制计算、分层”的基本目的；说明 MoE 层与 Attention 层可能使用不同的并行组织方式。采用具体框架的组定义画拓扑，避免用一个通用乘法公式概括所有部署。

## 6. 通信实现：token 如何到达远端专家？

本章回答：同一个分布式 MoE 计算，可以通过哪些通信路径实现？

### 6.1 先明确通信对象与范围

**写作要点：** token 隐藏状态、路由元数据、专家输出各自如何流动；是否跨节点或包含 TP。分析通信量时明确 T 的统计范围、数据类型、K 和专家分布。

### 6.2 AllGather 路径

AllGather 路径通常先在相应通信域汇集 token 输入，再由各 rank 计算本地专家负责的部分。结果侧还需要对应的聚合和分发，不能只画输入侧的 AllGather。

**待展开：** 参与的 group、路由信息如何获取、结果侧的集合通信、完整数据流和通信量估算。具体以第八章选定版本为准。

### 6.3 AlltoAll 路径

AlltoAll 路径根据专家路由，将 token 发给目标专家所在的 rank，完成专家计算后再进行结果回传与合并。

**待展开：** 按目标 rank 整理数据、发送与接收计数、按本地专家再次分组、输出恢复；区分逻辑上的按需分发与具体通信原语。

### 6.4 两条路径如何比较

| 比较维度 | 需要记录或分析的内容 |
| --- | --- |
| 数据传输 | 发送了哪些数据，是否有冗余，传输量如何计算？ |
| 数据整理 | 排序、重排、计数交换与额外缓冲的代价是什么？ |
| 工作负载 | T、K、EP 大小和路由倾斜如何影响执行？ |
| 硬件拓扑 | 单机与跨机带宽、时延是否改变结论？ |
| 实测性能 | 固定模型和配置后，延迟与吞吐分别如何？ |

避免脱离工作负载判断某条路径始终更快。

### 6.5 昇腾后端实现：MC2 与融合通信路径

本节承接通信方案，介绍昇腾侧的具体实现与优化。MC2 不作为与 AllGather、AlltoAll 同层级的第三种集合通信原语。

**待核实后展开：** 在选定 CANN 与 vLLM-Ascend 版本中，确认 MC2 对应的算子、输入输出、通信域、融合范围与约束；说明 token 整理、通信、计算、结果恢复中哪些步骤被融合或重叠，不能假定所有版本都包含相同功能。

## 7. 推理瓶颈与优化：激活参数少，为什么不一定快？

本章回答：如何从执行过程解释性能，并选择有依据的优化？

### 7.1 建立 MoE 层的耗时分解

**写作要点：** Router、重排、dispatch、专家计算、combine、同步等待；先画串行基线，再说明存在重叠时不能简单相加各阶段耗时。区分 MoE 层耗时与端到端请求延迟。

### 7.2 Prefill 与 Decode 的差异

**写作要点：** 每轮 token 数、每专家分配数量、矩阵形状和通信粒度如何变化；说明并发和调度方式的影响，不将 Prefill 或 Decode 固定归类为单一瓶颈。

### 7.3 按瓶颈组织优化方法

| 观察到的问题 | 可讨论的优化方向 | 需要验证的代价与限制 |
| --- | --- | --- |
| 专家小矩阵计算效率低 | Grouped GEMM、执行批量与算子调优 | 适用形状、缓冲和等待开销 |
| 权重访存或容量压力大 | 专家权重量化、部署布局调整 | 精度、反量化成本和硬件支持 |
| 重排与启动开销高 | 算子融合、减少中间数据搬运 | 融合范围、动态形状和版本约束 |
| 通信与同步开销高 | 通信路径选择、拓扑优化、通信计算重叠 | 额外资源、依赖关系和重叠效果 |
| 专家或设备负载倾斜 | 专家重放置、冗余专家、负载均衡 | 显存、迁移成本和映射维护 |

### 7.4 如何设计可复现的实验

**写作要点：** 固定模型、代码提交、硬件、并行配置、输入输出长度、并发和量化配置；记录每专家负载、通信耗时、计算耗时、缓冲占用，以及 TTFT、TPOT、吞吐等端到端指标。先确定瓶颈，再比较优化前后。

> 配图占位：Prefill / Decode 执行时间线，以及优化前后的阶段耗时对比。
